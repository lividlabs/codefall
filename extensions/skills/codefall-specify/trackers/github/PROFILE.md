# Tracker profile: github

**Status:** supported.

GitHub Issues, in the project's own repository — `github.issuesRepo` in `.codefall/settings.json`,
the one tracker a verb files on, per *Who is authoritative for what* in
`../../../../../.codefall/shared/workflow.md` — optionally placed on a GitHub Project. This is the
profile `codefall-specify` uses when the mirror's home is the same forge as the code.

**The spec document is canonical.** This profile creates and refreshes a mirror of it. Nothing here
holds a fact the document does not, and a hand-edited issue body is overwritten on the next run.

## Fits when

- The project's issues live in a GitHub repository, **and**
- `gh` is installed and authenticated against that repository.

## Does not fit

A GitHub Project used **without** repository issues. Project draft items are cards that live only in
the project: they have no issue number, carry no repository labels, and cannot be parents or children.

## Capabilities

| Capability | GitHub | What `codefall-specify` does |
| --- | --- | --- |
| Hierarchy | Native sub-issues | Spec issue is the parent; one child per requirement |
| Rich markup | GitHub-flavored Markdown | Body is written as plain Markdown, no translation |
| Labels | Repository-scoped, free-form | Two skill-owned labels; see below |
| Draft state | **Absent** | A `draft` label mirrors the spec's `Draft` status |
| Custom fields | Only via a Project, and per-installation | Optional; see "Project boards" |
| Image attachment from CLI | **Absent** | Mockups are referenced by repository path |
| Dependency links | Present, unused | `codefall-plan` owns dependency edges, not `codefall-specify` |

Two of those are absences worth stating plainly. **GitHub issues have no draft state** — the Projects
feature named "draft" is the unrelated card described above. And **`gh` cannot upload images**, which
is why mockups live in `docs/mockups/<slug>/` and the issue links to the path rather than embedding a
picture.

## Preconditions

`gh` must be authenticated with `repo` scope. Sub-issues are always used, so `read:project` and
`project` are required too:

```
gh auth refresh -s read:project -s project
```

If authentication is wrong, **the spec document is still written** — it is the deliverable. Give the
user that command, say the mirror is pending, and stop. Do not work around it.

## Issue shape

Two levels, both generated from the document.

**The spec issue** — one per spec, the parent.

```
Title:  SPEC-003: Trip itinerary export
```

```markdown
<!-- Generated by /specify from docs/specs/SPEC-003-trip-export.md. Edits here are overwritten. -->

**Spec:** [docs/specs/SPEC-003-trip-export.md](../blob/main/docs/specs/SPEC-003-trip-export.md)
**Vision:** docs/visions/VISION-002-trip-sharing.md

<the spec's Context section, verbatim>

## Requirements

- [ ] SPEC-003-REQ-01 — Export a saved trip
- [ ] SPEC-003-REQ-02 — Re-export after editing
```

**The requirement issue** — one per requirement, a sub-issue of the spec issue.

```
Title:  SPEC-003-REQ-01: Export a saved trip
```

```markdown
<!-- Generated by /specify from docs/specs/SPEC-003-trip-export.md. Edits here are overwritten. -->

**Spec:** [docs/specs/SPEC-003-trip-export.md](../blob/main/docs/specs/SPEC-003-trip-export.md)

As a traveler, I want to export a trip, so that I can share the itinerary with people who
aren't in the app.

## Acceptance criteria

- **SPEC-003-REQ-01-AC-01** — WHEN a traveler selects export on a trip that has a destination
  and both dates, the system SHALL produce a file containing the destination, departure date,
  return date, and traveler count
- **SPEC-003-REQ-01-AC-02** — IF the trip is missing a departure or return date, THEN the
  system SHALL make export unavailable and SHALL name the missing field

## Edge cases

- A trip edited while its export is running — the exported file may be stale; not addressed
  in this spec
```

**The requirement issue carries the criteria in full.** That is the whole reason this level exists:
somebody picking up the ticket sees what they have to satisfy without opening another file. The
spec-level sections — Key Entities, Assumptions, Existing behavior preserved, Out of scope, Open
questions — are **not** copied down; they live once, in the document, and the link is one click.

**The title carries the identifier**, which is how a later run finds the issue it already created.
Never retitle an issue by hand.

## Labels

This profile owns exactly two labels, and creates them if missing:

```bash
gh label create "draft" --color "BFBFBF" \
  --description "Specification incomplete — spec is still Draft" --force
gh label create "requires-mockup" --color "D93F0B" \
  --description "Blocked from planning until a mockup exists" --force
```

Both mirror the document, which is what `codefall-plan` reads; neither label is a state of its own.

`draft` **mirrors the spec's status** — present while the document says `Draft`, removed when it says
`Ready`. It is not an independent state, and it is applied to the spec issue and every requirement
issue alike.

`requires-mockup` mirrors a `Mockup: pending` line under a requirement's **Design notes**, applied per
requirement, and cleared when a mockup arrives rather than by this profile.

**`codefall-specify` does not impose a label taxonomy.** Type, domain, and component labels are the project's
own business, and a curated set baked into this profile would be wrong for every project that did not
choose it. Apply labels the repository already uses when the fit is obvious; invent none.

## Field mapping

| Specification | GitHub |
| --- | --- |
| `SPEC-NNN` and its title | Spec issue title |
| Context | Spec issue body |
| `SPEC-NNN-REQ-nn` and its title | Requirement issue title |
| User story, acceptance criteria, edge cases | Requirement issue body |
| Requirement belongs to spec | Sub-issue relation |
| `Status: Draft` | `draft` label on every issue in the set |
| `Status: Ready` | no `draft` label |
| `Status: Archived` | see "Archiving" |
| Mockup missing | `requires-mockup` on the affected requirement issues |
| Mockup present | Repository path in the spec's **Design notes** |
| Key Entities, Assumptions, Out of scope, Open questions, Existing behavior preserved | **Not mirrored.** Document only |

## Searching for duplicates

```bash
gh issue list --search "<keywords>" --state all \
  --json number,title,state,url,labels --limit 10
```

## Creating

One pass. Criteria are numbered from the spec identifier, which exists before GitHub is touched, so
there is no second pass to fill them in.

**Create the spec issue first**, then each requirement issue, then link them.

```bash
gh issue create --title "SPEC-003: Trip itinerary export" --body-file <spec-issue-body>
gh issue create --title "SPEC-003-REQ-01: Export a saved trip" --body-file <req-issue-body>
```

Use `--body-file` rather than `--body`. The bodies contain EARS criteria with parentheses, quotes, and
newlines, and passing those through a shell argument is where quoting goes wrong.

Link each requirement issue to the spec issue:

```bash
gh issue view <number> --json id --jq '.id'   # node ID for each issue
```

```bash
gh api graphql -f query='
  mutation {
    addSubIssue(input: { issueId: "<spec-issue-node-id>", subIssueId: "<requirement-issue-node-id>" }) {
      subIssue { number }
    }
  }'
```

Then write the spec issue's number into the document's `**Issue:**` line. That line is how the next
run finds the mirror.

The `blob/main` link in each body resolves once the spec's pull request merges. Until then the pull
request is where the document is, and its body carries `Relates to #<spec-issue>` so the two find
each other.

**`codefall-specify` writes no dependency links between issues.** GitHub supports them; ordering work is
`codefall-plan`'s decision, made against the build graph, and a guess recorded here would be a guess `codefall-plan`
has to unpick.

## Refreshing

When `codefall-specify` runs again on an existing spec, the mirror is regenerated rather than edited around.

1. Read the spec issue number from the document's `**Issue:**` line.
2. List its sub-issues and match each to a requirement by the identifier in the title.

   ```bash
   gh api graphql -f query='
     query {
       repository(owner: "<owner>", name: "<repo>") {
         issue(number: <spec-issue-number>) {
           subIssues(first: 50) { nodes { number title } }
         }
       }
     }'
   ```

3. **Existing requirement** — regenerate the body:

   ```bash
   gh issue edit <number> --body-file <regenerated-body>
   ```

4. **New requirement** — create it and add it as a sub-issue, as above.
5. **Requirement no longer in the document** — its number was retired. **Do not delete or close it
   silently.** Report it to the user and let them choose: close it, or leave it open because work
   already happened against it. A retired requirement whose ticket someone is holding is a
   conversation, not a cleanup.
6. Regenerate the spec issue body and reconcile the `draft` label against the document's status.

**Never reconcile in the other direction.** A body that differs from the document is a hand edit that
is about to be overwritten, which is what the generated-by comment at the top of every body says will
happen. If the user has been editing issue bodies expecting them to stick, say so plainly rather than
importing their text into the document.

## Archiving

When a spec is archived, its issues are not deleted — the identifiers stay resolvable.

Regenerate each body with the archived status and the new path, then ask the user what happens to the
issues. Closing them is usual; leaving one open because its work is still wanted is legitimate. Add
`Replaced by SPEC-NNN` to the body when the document carries that line.

Never close an issue without asking. Work state is the tracker's to hold, and this skill does not get
to decide that something stopped mattering.

## Project boards

Placing issues on a GitHub Project is **optional**, and this profile deliberately hardcodes nothing
about one.

Project IDs, field IDs, and single-select option IDs are **per-installation** values. They are not
properties of GitHub, and a profile that shipped them would work for exactly one repository. They have
to be discovered at run time:

```bash
gh project list --owner <owner>
gh project field-list <number> --owner <owner> --format json
```

Then place and set fields:

```bash
gh project item-add <number> --owner <owner> --url <issue-url>
gh project item-edit --project-id <project-node-id> --id <item-id> \
  --field-id <field-id> --single-select-option-id <option-id>
```

**This is the seam where per-project configuration belongs**, and it does not exist yet. Until it
does, ask the user whether issues go on a board, discover the IDs if they do, and skip the board
entirely if they do not. Never guess a field value, and never invent a workflow status the project
does not define.

Requirement issues are the ones worth boarding, because they are the unit of work. Ask before adding
the spec issue as well; on most boards a parent row is noise.

## Work-state transitions — `codefall-implement`'s

The mirror's lifecycle and labels are this profile's; the **work-state ladder on the spec's parent
issue** belongs to `codefall-implement`, which is the only verb that can observe the moments. It performs
exactly these transitions and no others:

| Moment | With a Project board | Without one |
| --- | --- | --- |
| First bead claimed | Status → **In Progress** | — |
| Work built, PRs open | Status → **In Review** | — |
| Every PR merged, epic closed | Status → **Done**, issue closed, requirement children closed with it | Issue closed, children with it |

Requirement sub-issues **never move individually** — beads carry plan refs, not requirement IDs,
so per-requirement status would be a guess, and a mirror that guesses is worse than one that is
coarse. The running trail is the `Relates to #<spec-issue>` line `codefall-implement` puts in every PR body.

Board IDs follow the rule above: discovered at run time, or read from the project's
`.codefall/skills/codefall-implement/CUSTOMIZE.md` when pinned there.

## Note on Beads

`bd github sync` moves issue **content** — title, body, labels, state, assignee. It does not move the
graph. Reading `internal/github/mapping.go` at `main`, the GitHub-to-beads conversion returns an empty
dependency list unconditionally, and the beads-to-GitHub direction sends only title, body, labels, and
state. Sub-issue relations and dependency links are invisible to it in both directions.

So the spec-to-requirement structure written here does not reach Beads through sync. `codefall-plan` reads
hierarchy from GitHub directly, and from the spec document, which holds it in a form sync cannot lose.
