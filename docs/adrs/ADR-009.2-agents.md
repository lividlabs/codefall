# ADR-009.2: Agents

## Status

Superseded by ADR-009.3 — 2026-09-28

## Context

ADR-009 gave codefall a way to reach for another agent than the session running it: a reviewer for
`review`, and a second opinion, a consult, for a run that cannot settle a question on its own. It
settled what still holds: an agent runs on a harness named for its binary or on `current`, the harness
running the session; a run tries agents in order, skips one this machine cannot start, moves on when
one fails or cannot settle the question, tries each once, and names every one tried; `via=` overrides
for one run; the agent states which harness it is in, because every harness says so in its prompt; a
consult proposes and the session decides; and all of it is project configuration, checked in.

What did not hold was the shape of the configuration. ADR-009 put a project-wide list of named agents
at the top level, gave `review` and `consult` each an optional order picked from it, and added a
per-harness override, `agentsByHarness`, on top. That was four keys and a precedence rule, and it came
from a misreading: the two sketches that asked for a harness-specific configuration were two spellings
of one design, agents keyed by the harness the session is running in, and they were built as a flat
list with the harness idea bolted on. The interactive editor exposed the cost. Its per-harness screen
read "none set; every harness walks the wider order", which nobody could read without this record in
hand, and its agents screen said the list was tried in order when, with a feature's order set, the
list's order did nothing.

The question a person asks is "I am in Muse; who reviews, who consults?" The configuration should be
shaped like the question. Nothing had been released, so the shape could change with no migration.

## Decision

### The list is keyed by the active agent

`.codefall/settings.json` carries an optional top-level `agents` array. Each entry is for one **active
agent**, the harness the session is running in: one of the five harness names, or `default`, which
covers every harness without an entry of its own. Each value appears at most once. An entry holds a
`review` list and a `consult` list, each an ordered array of agents, each agent a `harness`, one of the
five names or `current`, and optionally a `model`, passed to that harness as written.

```json
"agents": [
  {
    "activeAgent": "default",
    "review":  [ { "harness": "current" } ],
    "consult": [ { "harness": "current" } ]
  },
  {
    "activeAgent": "muse",
    "review":  [ { "harness": "claude" }, { "harness": "codex", "model": "gpt-5-codex" } ],
    "consult": [ { "harness": "claude" } ]
  }
],
"review": { "postToPullRequest": true }
```

The array is written for readability over lookup: every entry names what it is for, and validation
refuses a duplicate `activeAgent`, which a map keyed by harness would have made impossible to write
but no easier to read.

### One rule

A session resolves the list it tries for a feature in one step: the entry for the harness it is
running in, else the `default` entry; within that entry, the feature's list. A list left out of an
entry means the `default` entry's list; a `default` entry left out means one agent, `current`. A list
that is present holds at least one agent, because an empty list would say the same thing as leaving
the key out, a second way.

Absent, the whole array means one `default` entry whose two lists each hold `current`, which is what
every verb did before the list existed. `codefall init` writes that entry explicitly into a new
project's settings, and adds nothing to a project's existing file.

### Nothing else names an agent

The definitions list and its agent names go: an agent is its harness and model, written inline where
it is tried, and there is nothing to define elsewhere. `review.agents`, `consult.agents`, and
`agentsByHarness` go with them. `review.postToPullRequest` stays where it is, since posting does not
vary by harness. `via=` takes only the raw form, `harness[:model]`.

### Whoami stays

The agent still states which harness it is running in, from the five names, checked against the
directory the skill was loaded from. It is what picks the entry. A harness the agent cannot name is
`unknown`, and an unknown active agent reads the `default` entry, which is what it would have read
without one.

### Doctor and config

`doctor` warns about a harness any list names that is not on PATH, and about any list that names no
agent on `current`, so a project that wants a hard stop when its external reviewer is down is told
what it has chosen. `codefall config` edits the list by active agent and feature, in an editor whose
menu is Agents, Reviews, and Persona, and in a scripted form that reads as the question does:
`codefall config agents muse review claude codex:gpt-5-codex`.

## Alternatives

**Keeping the flat list with per-feature orders and a per-harness override.** Everything a person
needs was expressible, and nothing was readable: four keys, a precedence rule, and agent names to
invent. Set aside because a reader of the file had to know this record to predict which agent runs.

**Dropping the harness dimension.** A single flat list with review and consult orders explains itself
in one sentence, and it cannot say the one thing the harness dimension exists for: that a session in
Muse should have Claude review while a session in Claude Code should not. Set aside because the case
is real and was the origin of the whole design.

**A map keyed by harness.** `"agents": { "default": {…}, "muse": {…} }` is a direct lookup and
cannot hold a duplicate. Set aside for the array, which reads as a list of "when I am in X" entries,
because the file is read by people far more often than it is looked up by code, and validation covers
the duplicate.

**Agent names.** A name let `via=` say `via=architect` and let a report say who ran in one word. Set
aside because a name is one more thing to define and keep unique, and `harness:model` says the same
thing without a definitions list.

## Consequences

- **The configuration is shaped like the question.** A person opens `settings.json`, finds the
  harness they are sitting in, and reads who reviews and who consults. There is nothing else to
  cross-reference.
- **The override is gone, and with it the precedence rule.** There is one lookup, active agent then
  `default`, and one fallback, `current`.
- **Agents repeat across entries.** The same `codex:gpt-5-codex` may appear in several lists, where a
  named agent was written once. That is more text and no more meaning, and it is what makes each
  entry readable on its own.
- **`via=` loses names.** `via=codex:gpt-5-codex` is longer than `via=architect`, and it is exactly
  what the file says, so a report and the file agree without translation.
- **Review records written under ADR-009 carry a `reviewer.name`.** The findings schema keeps the
  field optional so the records under `.codefall/reviews/` stay valid; nothing new writes it.
- **The skills' resolution section shrinks to one rule.** `running-agents.md` says: your harness's
  entry, else `default`; the feature's list; try in order.
- **`doctor`'s current check is per list.** It reports "muse review names no agent on current" rather
  than a settings path, because the list is what the person edits.
