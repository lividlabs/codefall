# ADR-009.7: Agents

## Status

Accepted — 2026-10-26

## Context

ADR-009.6 carried seven decisions forward and recorded that the codefall OpenCode plugin does not
load under OpenCode 2.1.4, which left every OpenCode session without the plugin's merge guard and
session notice (issue #231). This record carries all seven decisions forward and changes two
things inside them: the codefall plugin is now in OpenCode 2's form, so it loads and runs in every
OpenCode run, and both scripts start every harness with `CODEFALL_HEADLESS=1`, which the session
notice reads and the merge guard does not. ADR-009.6 named the choice not to set
`OPENCODE_CONFIG_PROJECT_DISABLE` for revisiting once the plugin loaded; this record revisits it and
keeps it unset.

Issue #231 asked what the plugin needs to be in OpenCode 2's form, and whether its two hooks still
have somewhere to stand. Checked on OpenCode 2.1.4 with private servers and a scratch database, and
a local stand-in for a model so that no model ran, then once with a real model (the last item):

- **The form.** The loader accepts a default export that is a plain object with an `id` and a
  `setup` function, with no import from `@opencode/plugin`. A file at `.opencode/plugins/` is found,
  from a subdirectory of the project too, where it loads as its own instance for that directory. The
  plugin runs in a Bun runtime inside the binary, 1.4.4 in 2.1.4: `node:child_process`, `node:fs`,
  `Bun.spawn`, `Bun.file`, and `import.meta.dir` are present, and OpenCode 1's `$` helper is not.
- **The shell tool is named `shell`**, not `bash`, and takes `command`, `workdir`, `timeout`, and
  `background`. `ctx.tool.hook("execute.before", ...)` receives `tool`, `sessionID`, `agent`,
  `messageID`, `id`, and `input`. A thrown error stops the call before it runs: the tool is recorded
  as not executed, and the model reads the error's message as the tool's result. The permission
  `evaluate` hook, the other way to deny, was not needed. The permission block `run-worker.sh`
  writes names `bash`, and 2.1.4 applies a `bash` rule to the `shell` tool the way it applies a
  `shell` rule: a deny rule on `echo*` under either name refused an `echo`.
- **There is no session-start hook.** `ctx.event.subscribe()` delivers `session.created`, with the
  session in `data.sessionID` and, for a child session, a `data.parentID`; the field is in the
  event's schema, and no child session was created in these checks. The stream reaches every plugin
  instance on a server whatever directory the session is in, so a plugin that acts on it has to
  filter on `event.location.directory`.
- **`ctx.session.synthetic({ sessionID, text, resume: false })` adds a message without starting a
  turn.** The model reads it as a user message ahead of the next prompt, once; it stays in context
  without being added again. Called from the `session.created` handler it also works in `opencode
  run --standalone`, where the prompt follows the session at once: the message arrives while the
  first request is in flight, and the model reads it from the next step.
- **Plugins load under `opencode run --standalone`**, and the environment of the `run` process
  reaches them, because the private server is that process.
- **A real run.** `opencode run --standalone --model digitalocean/glm-5.3#max`, in a scratch
  repository with the plugin and the shared scripts installed, a checkout on `main`, and a local
  bare repository as `origin`, was told to run `git push origin main` and report its output. With
  `CODEFALL_HEADLESS=1` the guard refused the push, the model reported the guard's message, the bare
  repository did not receive the commit, and the session held no notice. Without the variable the
  guard refused the same push, the notice was added to the session, and the model followed it into
  `codefall init` instead of stopping, which is what the variable is for.

ADR-009.6's context follows as it was written. Where it says the codefall plugin does not load, it
describes the plugin released in 0.35.0, which this record replaces.

ADR-009.5 made seven decisions. Three are about how a harness is called, and carry ADR-009.4's
forward: `harnessConfig`, the scripts that apply it, and a findings schema with no `if`/`then`
clause. Four are about building in another harness: a runner that writes beside the one that reads,
a `work` list beside `review` and `consult`, review's fixes through that same list, and five guards
standing where the host's hooks would have. This record carries all seven forward and changes two
things inside them: which OpenCode versions codefall supports, now OpenCode 2 only, and the flags
`run-agent.sh` and `run-worker.sh` pass it.

ADR-009.5 wrote the OpenCode calls from what was known when it was written. `run-agent.sh` passed
`--pure`, which ran OpenCode without external plugins, and not `--standalone`. `run-worker.sh` passed
`--pure` and `--standalone` only when `opencode run --help` listed them, because OpenCode 2 had been
seen to refuse `--pure`, and ADR-009.5 said that `run-agent.sh`'s call did not pass `--standalone`
and that this was tracked separately. That item is issue #228. Checked against OpenCode 2.1.4:

- `opencode run --pure` fails with `Unrecognized flag: --pure in command opencode run` and exits 1
  before the model starts. So every OpenCode review or consult through `run-agent.sh` has exited 76
  and been skipped, which is the outcome #215 had on OpenCode 1.19.0, from a different cause.
- Without `--standalone`, `opencode run` sends the request to a background service that may have
  been started elsewhere. The run's PATH, working directory, and environment, including
  `OPENCODE_CONFIG_CONTENT` and the exports of a `harnessConfig` `env` command, may then not reach
  the process that runs the tools.
- `--file` is a single string in 2.1.4, not an array. Putting the message before `--file` (#215) is
  still correct and stays.

Dropping `--pure` raises the question ADR-009.4 answered by turning hooks off: does a headless run
now load the project's OpenCode plugin and follow its session hooks into a refresh instead of
answering? It was checked on 2.1.4 without a model run, by starting a private server in a project
that holds `.opencode/plugins/codefall.js` and reading the plugin list from the server's API:

- **The codefall plugin does not load.** OpenCode 2 accepts a plugin module only when it has a
  default export with an `id` and an `effect` or `setup` function. The codefall plugin is a named
  export, `CodefallPlugin`, in OpenCode 1's form, and the server lists it as failed with `Plugin must
  export a default definition with an id and an effect or setup function.` So under 2.1.4 neither
  its session notice nor its merge guard runs, in a headless run or any other. ADR-009.5 said the
  opposite, from the absence of a switch and not from a listing.
- **A plugin in OpenCode 2's form does load and run**, and no switch keeps exactly it out. An empty
  `plugin` or `plugins` list in `OPENCODE_CONFIG_CONTENT` changes nothing. A `"-<id>"` entry removes
  a plugin by its id, and the codefall plugin has none. `"-*"` removes every plugin but two,
  OpenCode's own providers and agents among them. `OPENCODE_CONFIG_PROJECT_DISABLE=1`, or
  `OPENCODE_DISABLE_PROJECT_CONFIG=1`, set for a private server, drops every project configuration
  source, the project's plugins with them, and a plugin in OpenCode 2's form then did not run.

The rest of this context is ADR-009.5's.

ADR-009.4 settled how codefall reaches an agent in another harness: who reviews and consults, in
the `agents` lists, and how each harness is called, in `harnessConfig`. Every agent it reaches
reads and proposes. `run-agent.sh` starts each harness in its read-only mode, and its header gives
the reason: a subprocess that edits bypasses the host's PreToolUse hooks and its checkpoints, so
nothing it did would be guarded or reversible. So `codefall-implement` could choose only a model at
its gate, and every worker was a subagent of the session's own harness.

A project built beads in another harness by hand twice. One implement round ran sixteen
single-bead workers on OpenCode with a cheaper model; each took 6 to 28 minutes and cost $0.33 to
$2.78, and all were accepted after the root's review. Another worker applied a review's seven fixes
in 46 minutes. Each time the root session rebuilt the guards from notes, and each time something
went wrong that a script settles once:

- macOS has no `timeout`, so one launch exited 127 before OpenCode started.
- One launch used OpenCode's `--auto`, which approves every permission a rule does not deny.
  Claude Code's auto-mode classifier then refused the session's next command as creating an unsafe
  agent. A scoped permission block in `OPENCODE_CONFIG_CONTENT`, with no `--auto`, was accepted.
- Blocking `bd` for the worker's whole process tree also blocked the beads git hooks, which run
  `bd hooks run pre-commit` and `bd hooks run prepare-commit-msg` on every commit. The worker could
  commit only by emptying `core.hooksPath`, so its commits skipped the hooks.
- `codefall-block-merge-to-main.sh` refused the root's own command that wrote the push-blocking
  shim, because the command contained a bare `git push` while the primary checkout was on `main`.
- OpenCode's `--file` took the message as a second file (#215).

What made those runs acceptable was where the work landed: a worktree on a branch of its own, which
the root read in full before anything left the machine. A worktree is where the work goes, not a
boundary: OpenCode's shell could have written anywhere the user can. What was missing was guards
standing where the host's hooks would have, a check on the one place outside the worktree whose
changes run later in the root's own session, and a written list of what the root does before and
after.

The rest of this context is ADR-009.4's. ADR-009.2 settled who codefall reaches for: an `agents`
list keyed by the harness the session is running in, each entry holding ordered lists of agents,
each a `harness` and an optional `model`. The first runs through Bedrock then showed that nothing in
a project could say how a harness is called: codex reached Bedrock through an AWS SDK that could not
refresh an `aws login` session the AWS CLI could, the findings schema's `if`/`then` clause was
rejected by Bedrock's structured output, and a headless run loaded the project's session-start
hooks and followed them into a refresh instead of answering. The model string is part of how a
harness is called, and it is easy to get wrong: the same model is `gpt-6-astra` direct,
`us.openai.gpt-6-astra` on Bedrock, and `amazon-bedrock/us.openai.gpt-6-astra` in OpenCode.
ADR-009.3 also had equip set a harness up only from inside it, which ADR-009.4 dropped.

### Options considered

**A mode flag on `run-agent.sh`.** One script, one copy of the agent syntax and the timeout. But
every reviewer and consult would then be read-only because a flag was left off, the header's
argument would become a condition, and a mistake in handling the flag would turn a reviewer into a
writer. Set aside: the read-only runner stays read-only by construction, and the runner that writes
is its own file, with its own header saying why it may.

**Renaming `run-agent.sh`**, to mark the pair as reader and writer. Clearer names, and a breaking
change: every installed skill and every script that calls it by path, an eval driver among them,
would need an upgrade for a name. Set aside; the new script's name says what it does.

**Extracting the shared parts into a common file.** It removes the copy, but it means editing
`run-agent.sh`, and the shared parts are short. Set aside: they are copied, and both headers say
the copies change together.

**A blanket approval**: OpenCode's `--auto`, Claude Code's `--dangerously-skip-permissions`,
Codex's bypass of approvals and sandbox. The simplest launch, and the one that got the host
session's next command refused, and it leaves nothing between the model and a push but the shims.
Set aside for each harness's scoped mode.

**Blocking `bd` outright for the worker.** It follows "workers never run `bd`" to the letter and
stops every commit, because the git hooks call `bd`. Set aside for a shim that lets `bd hooks run`
through: git calling `bd` is not the worker calling it.

**The worker pushes and opens its pull request**, as a subagent worker does. It saves the root a
step and removes the review that stands between a cheaper model and the remote. Set aside: the root
pushes after it has reviewed the branch.

**A list of its own for review's fixes.** It would let a project trust one harness to build and
another to fix. But both write code to a branch the root pushes, under the same guards, and two
lists would be two places to decide the same thing. Set aside for the one `work` list.

**Muse and agy as workers.** Both have read-only modes and no write mode scoped this way. Running
either with writes unscoped would be the blanket approval by another name. Set aside until each has
one.

**Supporting OpenCode 1.x and 2.x by reading `opencode run --help`.** `run-worker.sh` briefly did
this, passing `--standalone` and `--pure` only when the help listed them, and the same detection
would have fixed `run-agent.sh`. It keeps one script working across both versions, at the cost of
reading help text whose format is not a contract, a flag set that differs by what is installed, and
a second version of OpenCode to understand and test. Set aside: the user chose OpenCode 2 only, for
simplicity and for independence from the help text, and a project on 1.x upgrades once.

**Setting `OPENCODE_CONFIG_PROJECT_DISABLE` in both scripts**, to keep project plugins out of the
run. It works for plugins, as checked above, and it also drops the rest of the project's OpenCode
configuration: its `opencode.json`, and anything under its `.opencode` directory. A reviewer or
worker that needs the project's provider settings would then not reach its model. Set aside: there
is no plugin to exclude today, since the codefall plugin does not load, and the cost lands on every
OpenCode run. It is the first option to look at if a plugin in OpenCode 2's form ships.

That option was revisited with #231, as ADR-009.6 said it should be, now that a plugin in OpenCode
2's form ships. It stays set aside. The plugin has two parts, and a headless run should keep only
one: the merge guard is wanted in every run, and the session notice is what a run with a prompt to
answer must not get. The switch drops both, and the project's OpenCode configuration with them.

**Removing the plugin by its id**, `-codefall`, in `OPENCODE_CONFIG_CONTENT`. The plugin now has an
id, so this is possible, and it was not tried. Set aside for the same reason: it removes the guard
with the notice.

**A variable that only OpenCode's plugin reads.** The plugin is the one place that needs it today.
Set aside for one variable with one meaning in every harness: Claude Code and Codex run with their
hooks off in these scripts, but a project that turned them back on through `args` still gets a
quiet notice, because the notice script reads the variable whichever harness runs it.

**Priming through the plugin's `context` hook**, which runs before every model request, with a
record of which sessions were primed. Set aside: the event and the synthetic message work, and the
hook would make the first request wait for the notice and give the plugin state to keep.

**`"-*"` in `OPENCODE_CONFIG_CONTENT`.** It removes plugins by wildcard and takes OpenCode's own
built-in plugins with them. Set aside: it breaks the run.

**Leaving `--standalone` off `run-agent.sh`**, as ADR-009.5 did and said was tracked separately. A
reviewer reaching its model through an `env` command's exports, or through a PATH set by the caller,
may not have them in the background service. Set aside for the same flag `run-worker.sh` already
passes.

## Decision

### OpenCode 2 is the only supported OpenCode

Codefall supports OpenCode 2 and later. A project on OpenCode 1.x upgrades OpenCode by hand, which
makes this change breaking. `running-agents.md`, the configuration guide, the setup guide, and the
README say so. `codefall-equip`'s agents track reads `opencode --version` before it sets an OpenCode
agent up, and when it finds 1.x it says to upgrade and writes nothing. `codefall doctor` is not
changed: it runs nothing a project declares (ADR-009.4), and a version is read by running the
binary.

### `harnessConfig` says how a harness is called

Carried forward from ADR-009.4 unchanged. `.codefall/settings.json` carries an optional top-level
`harnessConfig` object, keyed by name. A key that is one of the five harness names configures that
harness. Any other key is a variant whose `harness` field names the binary, so a project can call
codex two ways. A block may carry `modelFlag`, the flag the model is passed with (default
`--model`); `provider`, the harness's own provider name; `args`, extra arguments appended as given;
and `env`, a shell command whose standard output is evaluated before the harness starts, so its
`export` lines take effect.

```json
"harnessConfig": {
  "codex": {
    "provider": "amazon-bedrock-runtime",
    "args": ["-c", "model_reasoning_effort=high"],
    "env": "aws configure export-credentials --format env"
  },
  "codex-direct": {
    "harness": "codex",
    "args": ["-c", "model_reasoning_effort=high"]
  }
}
```

A list item's `harness` is the lookup key, and so is the harness in a `via=` value. A list item
carries nothing else: the block is where how-to-call lives, once per harness. A harness name with no
block runs bare.

### The scripts apply it

`run-agent.sh` reads the block with jq when settings and jq are present, turns `provider` into the
harness's own switch (codex's `-c model_provider=`, Claude Code's `CLAUDE_CODE_USE_*` variables,
OpenCode's `provider/model` form; Muse and agy have no switch and refuse the field), appends `args`,
and evaluates the `env` command inside the run's timeout. `run-worker.sh`, below, reads the block
the same way. Every harness with a switch for its hooks runs with them off in both scripts: the
project's session-start hooks run `bd prime` and the refresh notice, and a headless run has been
seen to follow them instead of the prompt. OpenCode 2 has no switch for its hooks alone.

Both scripts call OpenCode the same way: `opencode run`, always with `--standalone`, never with
`--pure`, and with the message before `--file`. `--standalone` runs a private server that inherits
the script's PATH, working directory, and environment. `--pure` is refused by OpenCode 2 and is not
passed. Neither script reads `opencode run --help`. The flags are copied between the scripts, and
both headers say a change to one is made to the other. No project plugin is kept out of an
OpenCode run: the switch that would drop plugins also drops the project's OpenCode configuration,
so it is not set, and the project's plugins load, codefall's among them. What a headless run is kept
out of is the session notice, below.

### Headless runs say so

Both scripts set `CODEFALL_HEADLESS=1` in the environment of every harness they start, in the job
that runs the harness and ahead of the harness's own call. It means one thing in every harness: this
run has a prompt to answer, and nothing should prime it. `codefall-session-notice.sh` exits without
a word when it is set, so the Claude Code and Codex `SessionStart` entries and the OpenCode plugin
all stand down for it, and the plugin skips the Beads prime with it. The `bd prime --hook-json`
entry in Claude Code's and Codex's definitions is Beads' command and does not read the variable;
those two harnesses run with their hooks off in these scripts. The merge guard reads nothing of the
kind and stays on in every run. The variable reaches a `--standalone` run, which is the only kind
the scripts start.

### The OpenCode plugin is in OpenCode 2's form

`extensions/hooks/opencode/codefall.js` is a default export with the id `codefall` and a `setup`
function, a plain object so that a project needs no `@opencode/plugin`. It stays an adapter to the
shared scripts in `.codefall/hooks/shared/`, found from `import.meta.dir`, and does nothing when a
script is missing.

- **The merge guard** is `ctx.tool.hook("execute.before", ...)` on the `shell` tool. It builds the
  same Claude-shaped payload the other harnesses send, pipes it to
  `codefall-block-merge-to-main.sh` with no shell in between, from the tool's `workdir` when the call
  names one, and throws the script's stderr when the script exits non-zero. A script that is missing
  or cannot start lets the call through, as before.
- **The session notice** is the `session.created` event, for sessions of the plugin's own directory
  that have no parent. It runs `bd prime` and `codefall-session-notice.sh` once and adds their output
  as one synthetic message with `resume: false`. Every failure is swallowed, and nothing happens when
  `CODEFALL_HEADLESS` is set.

### The schema stops saying what only some validators accept

Carried forward from ADR-009.4 unchanged. The findings schema has no `if`/`then` clause, and triage
asks for the reason before it writes a dismissal. A rule the schema cannot state in a form every
harness accepts belongs where it is applied.

### A runner that writes, beside the one that reads

`extensions/shared/run-worker.sh <agent> <worktree> <prompt-file> <out-file>` runs one worker in
another harness, with the worktree as its working directory. It takes the same agents as
`run-agent.sh`, `<harness>[:<model>]`, `current`, or a `harnessConfig` key; reads the same block;
polls the same process-group timeout, under its own `CODEFALL_WORK_TIMEOUT`, an hour by default;
and exits with the same codes meaning the same things, plus 77 for the git-directory check below,
which a reader never needs. The worker's final message goes to the
out-file and the transcript to `<out-file>.transcript`. `run-agent.sh` is unchanged. The parts the
two share are copied, and both headers say a change to one is made to the other.

### A `work` list beside `review` and `consult`

Each `agents` entry may hold a `work` list, the agents `codefall-implement` offers to build a bead,
resolved by the same rule as the other two: the session's entry, else the default entry, else
`current`. `codefall init` does not write one, since an absent list already resolves to `current`,
which is what implement did before the list existed. `codefall config agents <activeAgent> work`
writes it, the editor shows it, and doctor's two agent checks cover it. Implement's gate proposes
one agent per bead from the list, and the person changes any of them there. The bead's comment
records `built with <harness>:<model>`.

### Review's fixes may use a worker too

`codefall-review` applies the fixes the person takes in its own session, or, when the fixes land on
a branch or an open pull request and the person picks one at triage, through one worker from the
same `work` list, not a list of its own: which agents may write code is one decision for a project,
whichever verb asks. The root creates a worktree on a local branch off the target's branch and
installs the dependencies; the worker applies every accepted fix and commits; the root restores
anything the git-directory check names, reviews the diff against the accepted findings, re-runs the
checks, breaks the code any new test covers, writes and commits the findings files, and pushes to
the target's branch with the branch named. A worker is never given uncommitted work, a path on the
default branch, or an epic's code findings, which `codefall-implement` builds.

### The guards

A worker writes, so five things stand where the host's hooks would have. They narrow what a
worker can reach; only Codex's sandbox confines it. A Codex worker's commands can write the
worktree and the repository's common git directory, nothing else, with the network off. A Claude
Code or OpenCode worker's file tools stay in the worktree, but its shell can write anywhere the user
can, apart from the commands denied to it.

1. **Scoped permissions in each harness's build mode, never a blanket approval.** OpenCode runs its
   `build` agent with a permission block in `OPENCODE_CONFIG_CONTENT`, set at the top level and on
   the agent: edits allowed; the shell allowed except `git push*`, `gh`, and `bd`; web fetch, web
   search, and directories outside the worktree denied. It runs on a private server, so the block,
   the PATH, and the working directory reach the tools. Claude Code runs in `acceptEdits` with the
   shell allowed and deny rules for `git push`, `gh`, `bd`, and the web tools, and with nobody to
   answer a prompt, so anything else that would ask is denied. Codex runs in its `workspace-write`
   sandbox with the network off and the repository's common git directory writable, so a worktree
   can commit. Muse and agy exit 64.
2. **Shims first on the worker's PATH.** `git` refuses `push` and `send-pack` and passes everything
   else to the real git; `gh` refuses everything; `bd` refuses everything except `bd hooks run`. Each
   names the real binary by absolute path, so it never finds itself, and the directory is removed
   when the run ends.
3. **Hooks off** where the harness has a switch, as in `run-agent.sh`. OpenCode 2 has none, so its
   plugin loads: its merge guard runs on the worker's shell commands, and its session notice stands
   down for `CODEFALL_HEADLESS`.
4. **A check on the git directory.** Before the run the script records the repository's config, the
   worktree's own config, the common `hooks` directory, and the `core.hooksPath` directory when it
   is outside the worktree, each file's checksum and whether it is executable, held in memory where
   the worker cannot reach it. After the run it compares them, names every file added, removed, or
   changed, and exits 77, whatever the harness's own outcome, which the message still names. A
   planted hook or config entry would run in the root's next git command, with the network on, and
   the diff never shows it. 77 sits with 73, 75, and 76 as a run that failed, with one thing to do
   before advancing: inspect and restore what it names. The script is one braced block, so bash
   has read all of it before the worker starts and a rewrite of the file mid-run changes nothing.
5. **The root's duties, written in `codefall-implement`.** Before the run the root creates the
   worktree and installs the dependencies, since the worker may have no network. `codefall-review`
   holds the same duties for the fixes it gives a worker, below. After it the root
   restores anything the git-directory check names, reviews the diff against the bead's criteria, re-runs the project's checks, breaks the code each
   new test covers and confirms the test fails, confirms the model the harness ran, and pushes and
   opens the pull request itself. The worker never runs `bd`, never pushes, and never opens a pull
   request.

For OpenCode, the model and variant a run used are in the session it records,
`session_v2.model` in `~/.local/share/opencode/opencode.db`, and the script prints them after the
run, read with `sqlite3 -readonly`. A variant OpenCode does not know fails the run rather than
falling back to another.

## Consequences

- **A bead can be built by another harness and model**, chosen per bead at the gate, through the
  same settings that already say how each harness is called. A mechanical bead can go to a model
  that costs a fraction of the session's.
- **The read-only runner keeps its guarantee.** Nothing a reviewer or a consult runs can write,
  whatever a caller passes.
- **Two scripts carry the same agent, settings, timeout, and OpenCode flag logic.** A change to one
  is made to the other, and only review notices when it is not.
- **OpenCode's flags are fixed, not read from its help.** The scripts no longer adapt to the
  OpenCode installed, so a later OpenCode 2 release that renames a flag fails the run with
  OpenCode's own error and a 76, as 2.1.4 did for `--pure`.
- **What a bad run can cost depends on the harness.** A Codex worker reaches the worktree and the
  repository's git directory. A Claude Code or OpenCode worker's shell reaches anything the user
  can: other checkouts, the home directory, the shims themselves. The git-directory check covers
  the place whose changes would run in the root's own session; nothing covers the rest, and the
  root's review of the diff sees only the worktree. A project that cannot accept that runs workers
  on Codex, or not at all.
- **No guard is complete alone.** A login shell that rebuilds PATH can put the real git ahead of the
  shim; a permission rule matches the spellings it names; a shell can rewrite a shim; the
  git-directory check watches only the git directory.
- **A Codex worker can write the repository's whole git directory**, not only its own branch's refs,
  because a worktree's commits land there. The network being off keeps that on the machine, and the
  git-directory check reports a change to its config or hooks.
- **A project on OpenCode 1.x must upgrade by hand.** Until it does, an `opencode` entry in a review
  or consult list is not expected to run, and equip says to upgrade before it writes one.
- **The codefall plugin loads in every OpenCode run, and its merge guard runs in all of them.** A
  reviewer, a consult, a worker, and an interactive session each have it, a worker beside the shims
  and the permission block. It judges the command string, with the limits the script states about
  itself, and the repository ruleset is still the backstop.
- **The session notice reaches an OpenCode session after its first request has started.** There is
  no session-start hook, so the plugin adds the message when the session is created, and `bd prime`
  and the notice take a second or less. A prompt sent at once is already in flight, and the model
  reads the message from its next step. A session that waits for its first prompt has the message
  ahead of it; whether the terminal interface creates its session ahead of that prompt was not
  checked. A child session is not primed, since its parent was.
- **The variable covers the runs the scripts start.** A person who runs a harness by hand in a
  headless mode gets the notice unless they set it, and a run sent to OpenCode's background service
  does not carry the environment of the process that started it, which neither script does.
- **The plugin guards the tool named `shell`.** A release that renamed it would let every command
  through with no error, since the plugin judges only the name it knows. The first sign would be a
  push the guard did not stop.
- **An upgrade replaces the plugin.** `codefall upgrade` copies the shipped file over the installed
  one, so a project on 0.35.0 or earlier gets the plugin OpenCode 2 loads without doing anything by
  hand. A project that never upgrades keeps the one it refuses.
- **A Claude Code worker runs with `--bare`**, as a Claude reviewer does, which reads Anthropic
  credentials only from an API key or an `apiKeyHelper`; a machine signed in to Claude Code by OAuth
  alone cannot start one this way.
- **The root's time per bead grows**: a review, the checks again, a test broken on purpose, the push.
  That is the price of a cheaper model's code meeting the same bar as the session's.
- **Muse and agy cannot build** until each gains a write mode that can be scoped.
- **Review's fixes have the same reach and the same checks as a bead's.** A project that would not
  let a Claude Code or OpenCode worker build a bead should not pick one to apply fixes either; the
  `work` list is the one place both read.
