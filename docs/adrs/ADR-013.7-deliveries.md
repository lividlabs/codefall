# ADR-013.7: Deliveries

## Status

Accepted — 2026-10-28

## Context

The chain runs spec → plan → implement → review → test, and each verb hands what it finds forward
in a different form. Three of those forms left the epic's graph. `implement` filed a code discovery
as a task beside the graph, with a `discovered-from` edge but no parent. `review` applied accepted
findings in the session and left a deferred finding whose cause was the code in the findings file
alone, under a directory `.ignore` keeps out of search. `test` filed a tracker issue on the user's
word and stopped, and `fix` later opened a standalone bead for it. `test` was also written to run
after the merge: implement's scope said `codefall-test` owns what comes after the work lands.

So the task beads burned down to zero, the epic looked finished, and the work review and test had
found sat where no verb read at its start. In a real run the person lost track of the second of two
findings. Nothing named the unit between plan and merge either, so "session" meant both one
conversation and the whole effort, and the context cost of running every verb in one conversation
was treated as the price of not losing state.

The principle that decides all of it: **the work is not done until it is working, and done is read
from the graph.** Beads already refuses to close an epic while a child is open, and `implement` on
an epic already walks `bd ready --mol <epic>` until the ready set is empty and reconciles a re-run.
The burndown existed. The findings were not on it.

ADR-013 recorded this on 2026-09-30, ADR-013.2 corrected the chart and added the notes log on
2026-10-01, ADR-013.3 handed integration to GitHub's stacked pull requests on 2026-10-05,
ADR-013.4 made the link to the top pull request the whole merge instruction on 2026-10-06,
ADR-013.5 triaged bugs before filing them so that only the epic's went under the epic on
2026-10-19, and ADR-013.6 renamed the sweep epic a followup on 2026-10-21.

This edition changes how a delivery runs from one round to the next, and who decides along the
way. A delivery of a large epic took between nine and eleven rounds, and a person was needed at
every gate of every round. Three rules in the skills caused that, and one prompt showed what
removing them does.

**Every non-bug discovery was the epic's.** ADR-013.5 triaged a bug by whose it is, and left a
cleanup, a missing test, or a refactor as the epic's by rule: the work found it, so the next round
builds it. One epic ended with eighteen P4 cleanups as deferred children. A deferred child has one
reader, the next round of `implement`, which reopens it and builds it; `report`'s triage mode lists
parentless items only, and `fix` refuses a child of an epic whose merge gates are open. So
"deferred" meant "not this round" on the day it was filed and "stuck under this epic until someone
builds it" afterwards, and nothing in triage could say "this is not an issue" or "this is already
filed".

**The plan hand-off told the person to run a verb.** ADR-014 had every verb run the verb upstream
of it rather than telling the person to, and listed the cases. Plan was not among them from
`implement`, `review`, or `test`: a finding that moved work became a `plan-revision` bead, and the
report, the hand-off comment on the epic, and `review`'s close-out all said to run `/codefall-plan`.
`implement` could not have run it; its tool list had no `Skill`. Plan's Revise mode then made each
of its three outcomes the person's decision. A conflict with an ADR went back to plan "as a
conversation". The same epic ended with two ADR questions waiting on a person.

**A recommendation waited for a yes.** The skills' rule was that a skill reports and offers and
applies only what the user takes, and every gate followed it: the go gate, "Fix them all? (I
recommend yes.)", the bead offers, the Revise outcomes, the `.ignore` line. The consult, which
answers the run's own uncertainty, fired only on a worker failure, a `notChecked` entry, or a point
plan could not settle after research, and in practice never fired at all, because the questions
reaching the person were not questions the run could not answer. They were recommendations the
rule made it ask about.

A person then ran a delivery with one prompt: nobody is present, so ignore the go gates; when you
need guidance, consult the strongest model, and when the consult cannot settle it, record a human
bead and continue on the best judgment available; after implement run review, after review run
test, after test triage everything open and deferred, move a batch of high-value beads into the
round, and go again; a plan or spec that needs a change is changed in a pull request as part of a
round; keep going until the epic is nearly empty. It ran two rounds unattended and stopped in the
third on the harness's permission classifier, not on the skills. That prompt is what this edition
writes into the skills, with the parts the prompt left to judgment written down.

Two costs are accepted with it. A continuous delivery in one session compacts, and the tail of a
skill drops after compaction (ADR-004.2); every handoff is already an artifact, so state survives,
and the rule that keeps a run going lives at the top of the skill and is reloaded at each round
boundary. And a run that decides for itself can decide wrongly; the pull request a person merges
is the gate that was always there, and the ledger below is what they read before merging.

## Decision

### A decision policy, written once

`shared/decisions.md`, installed as `.codefall/shared/decisions.md`, is the rule every verb reads
in place of "applies only what the user takes". A recommendation the run can state the reason for
in a sentence, that is reversible, and that stays inside the run's scope is applied and reported,
not asked. Three kinds of question are not the run's to decide: a product decision, a
hard-to-reverse choice the project's stance gives no default for, and a preference the person has
stated. For those the run consults once, with the project's `consult` list walked as
ADR-009.7 says; an answer that settles it is applied; one that does not becomes a human bead, the
run takes the best default available, and continues. A run stops only when it cannot continue at
all. Every gate and confirmation a verb carries becomes a report under this policy, except the one
gate at the start of a delivery.

The consult prompt asks the agent, when it says a decision is a human's, to still name the option
it would take and why, so the human bead carries a recommended default and the run takes that one
rather than its own guess. The merge to `main` stays the one human gate for everything.

### A round is implement, review, test, then triage

A round is one run of `implement` to an empty frontier, then `review` on the epic's work, then
`test` on it, in that order. `review` and `test` file what they find as beads, per the triage
reference, and fix nothing and build nothing: the step where each ran `implement` on the epic
afterwards is removed. The round ends at `test`. At the start of the next round, before anything
is claimed, `implement` triages everything open or deferred under the epic and picks the batch:
every P1 and P2, plus whatever it judges high value with its reason stated. The rest stays
deferred, or moves beside the epic or into the area's followup, or closes. The round number stays
`implement`'s to set, at that boundary.

A later round's go is where `implement` runs `plan`'s Revise mode on the plan when
`plan-revision` beads were filed, and `review` and `test` run it in their own close-outs. The three
outcomes of Revise, amend the text, add a row, or reject, follow the decision policy. An ADR
question takes the default the project's stance gives, and plan writes the ADR into its own pull
request, as it already does when a product manager answers "settle now". The hand-off that told the
person to run plan is gone, and `implement` and `fix` gain the `Skill` tool to run it.

### Every item is triaged, with six dispositions

The triage reference asks "whose is it" of every item, a cleanup, a missing test, or a refactor as
much as a bug, and "filed as it stands" leaves `implement`'s workers reference. Three dispositions
join the epic's, beside it, and the followup: **this round**, filed `open` so the next wave's
`bd ready` takes it, for a mistake one worker made that another saw; **duplicate**, a comment on
the bead that already exists; and **not an issue**, never filed, listed in the report with the
reason. `implement` applies them at every wave boundary and once more over the whole list at the
round boundary, and `report`'s triage mode takes an epic as its argument and lists that epic's
deferred children with the same dispositions, so a deferred child has a way out that is not being
built.

### The ledger

A decision the run makes about one bead is written on that bead's notes, append-only, in the same
line form the epic's log uses, naming who decided: `decided (session): …` or
`decided (consult codex:astra): …`, with the date. A decision with no bead of its own, the landing
strategy, a plan amendment, the batch, goes on the epic. A question the consult could not settle is
a bead labelled for a human, a child of the epic, carrying the question and the default the run
took in its body. The epic's round line summarizes and names them:
`round 2 (implement) [date]: 5 tasks built, 3 decisions on T2 T4 T7, 1 question (bead X)`. The
rule that a close-out records in a `bd comment` what no artifact holds moves to notes with the
rest, so there is one ledger; comments keep the pull request link on each task bead and the consult
record on a failed one.

A human bead that is open keeps the epic from closing, as any child does. The merge link is given
when every child but the landed bead and the human beads is closed and the last test run passed;
the epic closes once the person has answered them.

### Continuous by default, with one gate

An epic-scope `implement` run shows one gate: the chart, the execution plan, the harness, model,
and effort per bead, the consult order, the batch for this round on a later round, the permissions
condition, the ceiling, and that the run continues through review, test, and the rounds after
until the delivery is done unless the person says to stop after this round. On go it runs rounds
without asking again. A run that stops for any reason names `/codefall-implement <epic>` as the way
to resume, and that gate shows the reason and the same default. `review` and `test` run on their
own stay single verbs and end with the next command.

The rule that keeps the run going is written as a situation and a procedure, not a prohibition,
near the top of the skill, and repeated at each place a run would otherwise stop.

### When a run stops

A reference file read at the round boundary opens with its purpose: stopping is for rounds that
will not bring the epic closer to done, and when the signals are mixed the round runs. Three exits
are mechanical, because they are what the run cannot do anything about: the delivery is done;
nothing in the batch can be built, because every bead is blocked on a human bead or has already
failed twice; and the round number is at the ceiling, ten by default, changed at the gate or in
`CUSTOMIZE.md`, counted per delivery in the epic's `round` metadata. Everything else is a signal
the run weighs with the default being to continue: a round that closed nothing, a batch that is not
shrinking, a finding class that repeats. Before stopping on signals the run consults once on
whether another round is likely to move the epic, and runs the round on a yes or no answer. Every
round boundary writes a judgment line to the epic's notes, the signals seen and what was decided.

### Waves first, then the strategy

`implement` builds the waves from the graph before it picks a landing strategy, and the waves'
shape picks it: every wave one bead wide is a chain and lands as a serial stack; any wave wider
than one lands on an epic branch. The gate shows the execution plan, the waves and their widths,
the branch diagram, and the strategy with its reason in a line, rather than offering a choice.
Later rounds keep the strategy round one used, and a standing preference in `CUSTOMIZE.md` or work
that must not land in increments still forces the epic branch.

### Effort per agent

The gate's per-bead table carries an effort beside the harness and model, proposed the way the
harness is: low or medium for a rename or a doc aligned with the code, high for a bead that needs
a design call, with the bead's execution metadata as the hint. The launch applies it: the `effort`
parameter of the current harness's subagent tool, OpenCode's `#variant` suffix on the model,
Codex's `model_reasoning_effort` argument, and `--effort` on Claude Code through `run-worker.sh`.
Reviewer subagents run at high, consults at high or max. The `/effort` recommendation at the gate is
gone; the root session's own effort is the person's to set before they leave, and the gate states
it.

## Consequences

- A delivery is one command. `/codefall-implement <epic>` runs to the merge link or to a stop it
  can name, and a person reads the ledger and the pull requests rather than answering gates.
- The skills' rule "a skill reports and offers; it applies only what the user takes" is replaced
  by the decision policy, which applies to every verb and not only to deliveries. Verbs outside a
  delivery ask fewer questions for the same reason.
- `review` and `test` are simpler: they file and report. The loop lives in `implement` and its
  rounds reference, which is one place to read when a delivery behaves badly.
- Non-bug items can now leave the epic. A delivery stays the size of the feature plus what is
  worth fixing with it, and an epic that reached eighteen cleanups would now reach a followup.
- The ledger is on the beads and the epic, where `bd show` reads it, and the human beads are
  children, so a person answers them before the epic closes.
- The consult list is where a project puts its strongest model first; the walk already falls back
  to `current` when that harness is missing or cannot settle the question.
- The ceiling and the signals are a starting point. The judgment lines each round writes are the
  evidence for adjusting them.
- `implement`'s `SKILL.md` carries more, and the preflight tables and the per-bead reading list
  that `fix` and the worker prompt already restate are shortened to stay inside ADR-004.2's
  budget.
- More than one delivery in flight at once is not addressed by this edition. The rules are written
  per epic and nothing forbids it; the steps that use the primary checkout's working tree, `test`'s
  checkout of the epic's branch and the merges at a wave boundary, are where two would collide,
  and a worktree per epic is the change if that is wanted.
