# ADR-013.5: Deliveries

## Status

Superseded by ADR-013.6 — 2026-10-21

## Context

The chain runs spec → plan → implement → review → test, and each verb hands what it finds forward
in a different form. Three of those forms left the epic's graph. `implement` filed a code discovery
as a task beside the graph, with a `discovered-from` edge but no parent. `review` applied accepted
findings in the session and left a deferred finding whose cause was the code in the findings file
alone, under a directory `.ignore` keeps out of search. `test` filed a tracker issue on the user's
word and stopped, and `fix` later opened a standalone bead for it. `test` was also written to run
after the merge: implement's scope said `codefall-test` owns what comes after the work lands.

So the task beads burned down to zero, the epic looked finished, and the work review and test had
found sat where no verb read at its start. In a real run the person lost track of the second of two
findings. Nothing named the unit between plan and merge either, so "session" meant both one
conversation and the whole effort, and the context cost of running every verb in one conversation
was treated as the price of not losing state.

The principle that decides all of it: **the work is not done until it is working, and done is read
from the graph.** Beads already refuses to close an epic while a child is open, and `implement` on
an epic already walks `bd ready --mol <epic>` until the ready set is empty and reconciles a re-run.
The burndown existed. The findings were not on it.

ADR-013 recorded this on 2026-09-30, ADR-013.2 corrected the chart and added the notes log on
2026-10-01, ADR-013.3 handed integration to GitHub's stacked pull requests on 2026-10-05, and
ADR-013.4 made the link to the top pull request the whole merge instruction on 2026-10-06.

This edition changes one section, *Every finding is a child of the epic*. That rule solved the
lost-finding problem by making the epic the only destination, and it never asked whether a finding
belonged there. In practice every bug a round found went under the epic whatever it was about: a
worker's tangent in a file the plan never named, a sweep anomaly on a page the feature did not
touch. Two costs followed. `fix` refuses a bead whose parent epic has open merge gates, so a bug
that had nothing to do with the delivery could not be fixed on `main` until the whole delivery
merged. And the next round of `implement` built every one of them on the epic's stack, so the
feature's pull requests grew to carry fixes nobody had asked the delivery for, and the delivery
could not close until they were done.

The bugs that did not belong also had nowhere else to go. A bead with no parent carried a title,
a priority from whichever verb's table filed it, and a `discovered-from` edge, and nothing said
which part of the product it was about, how big its fix was, or who had found it. One project
reached a hundred open bugs with no way to read them as anything but a list. Three verbs carried
three priority tables: review's blocker, important, and minor, test's by class so that a cosmetic
real bug was P1, and implement's flat P2. `report` set a severity and left priority to the team.

Two shapes for organization were considered and one rejected. A standing container epic per area
would never close, `delivery.sh` would chart it, and `implement` would take it as a delivery; an
epic in Beads exists to be emptied, and closing one is the point. Organization therefore lives on
the bug itself, as fields that survive any change of parent, and an epic is cut from the backlog
only when someone decides to deliver a batch.

## Decision

### Vocabulary

A **delivery** is the work on one epic from the plan's graph to the human merge, taken in
**rounds** of implement, review, and test. It ends when the epic has no open children and the last
test run against it passed. A **run** is one verb invocation; a **session** is one conversation.
A `/clear` between verbs is the intended way to run a delivery: every handoff is a bead, a document,
a report, or a pull request, so a fresh session loses nothing.

### Every finding is triaged, and the epic's findings are its children

Every finding that survives triage becomes a bead with a `discovered-from` or `caused-by` edge to
what found it. One that is not a bug — a missing test, a refactor, a `plan-revision` — is a child of
the epic as before, created `deferred` so `bd ready` does not hand it to the round still running,
and reopened at the next round's go. `plan-amended` beads are parented too, for a complete
`bd children`.

A bug is triaged first, by the shared reference `shared/triage.md`, installed as
`.codefall/shared/triage.md`, which every verb that files a bug points at and none restates. Three
questions: whose it is, how bad it is, which area. The session proposes the answers with a reason
each, and the person confirms them in the verb's own question.

**Whose it is** has three classes. A bug is the epic's when it stops the epic from shipping, when
the epic's changes caused it, or when it sits in code the epic is changing; who caused it does not
matter. It sits beside the epic when it is in a feature or component the epic never touched and the
epic ships fine with it still there. The rest is judged by three things together: near the work,
P1 to P3, and fixing it leaves the delivered work better. All three keep it with the epic. A P4
goes beside, and so does a fix that needs its own plan. The count of bugs already filed does not
enter the judgment; it was considered and left out until a run shows it is needed.

A bug that is the epic's is a `deferred` child of the epic, as every finding was. A bug beside the
epic is an `open` bead with no parent, or a child of the open sweep epic for its area when one
exists, and the round does not build it.

**How bad it is** is one scale for every bug, `report`'s severity scale: critical P1, major P2,
minor P3, trivial P4, by how bad the bug is for a user. Review's words stay and are that scale.
Test's real bugs take it; test's other classes are not bugs and keep their own routes.

**Which area** is one label, `area:<name>`, naming a part of the product as a person meets it. The
list of areas is the labels in use, read with `bd label list-all`, seeded from the testing root's
case directories, the scoped `AGENTS.md` directories, and the specs when none exists yet. No file
holds it, so filing a bug in the middle of a run changes nothing in the checkout.

**Every bug bead carries the same fields**, whichever verb files it: type `bug`, the priority, the
area label, the source edge, `caused-by` for a regression and `discovered-from` for a bug that was
already there, the spec or bug report as `spec_id`, the tracker issue as `external_ref`, and
`size` and `found` in metadata. `report` files one such bead per report, so the backlog is complete
from the moment a bug is known, and `plan` and `fix` fill that bead in rather than creating a
second.

### Sweeps

A sweep is an ordinary epic, `<prefix>-SWEEP-<area>-NNN`, cut by `report`'s triage mode from the
open bugs of one area that the person picks. It has no plan document; `implement` reads each child
as a tier-0 bead and runs the delivery as for any epic, and it closes when its bugs have merged. An
open sweep is where a new bug beside an epic in that area goes. No container that never closes is
created.

### What closes when

A task bead still closes at done — criteria verified, checks green, pull request open — because the
close is what releases the next link in a stack. The epic closes when the graph is empty and the
code is on `main`, and the graph is not empty while a child review or test filed is open. Done is a
query: `bd children <epic>` with nothing open but the landed bead, and the last test run against the
epic passed.

### Test runs before the merge

`test` takes an epic as a target: the cases the epic's children name, plus the suites the changed
files reach, run on the epic's branch or the stack's top, checked out in the primary checkout the way
`review` already checks a branch out for its fixes. Every other target behaves as before, so an ad
hoc case or a full suite before a release runs at any time.

### The round, the chart, and the log

The round number is `metadata.round` on the epic, a flat scalar written with `--set-metadata` by
`implement` alone, at the go gate of a re-entry run, so no bounce produces two bumps. It is the only
metadata a delivery keeps on the epic; structured blobs in metadata were considered and rejected as
a second thing to manage. A bug bead's `size` and `found` are metadata on the bug, not on the epic.

Every verb in a delivery prints one line from the shared `delivery.sh` at its start and in its
close-out: the epic, the round, and the children closed over the children in all, with a bar.

```
booking-PLAN-007 · round 2 · 10/12 ██████████████░░░
```

The counts are `bd epic status --json`'s own, every child included, so the chart, `bd show`, and
`bd epic status` agree on one number. The landed bead counts: once every task is closed and the
test passed, the one open child is "Land: all PRs merged to main", and the open item names the
next act.

Each of `implement`, `review`, and `test` appends one line to the epic's notes at its close-out,
with `--append-notes` and never `--notes`, so `bd show <epic>` reads as the delivery's history:

```
round 1 (implement) [2026-09-30]: 7 tasks built, PRs #101 #102
round 1 (review) [2026-09-30]: 3 fixed, 2 deferred as children
round 1 (test) [2026-09-30]: FAIL 2/7, 1 child filed, 1 bug filed beside
```

The round, the verb in parentheses, the date in brackets, a colon, then what happened in words.
Comments keep their current job: the PR link on each task bead, the revision hand-off, and anything
decided in conversation that no artifact holds, which a verb's close-out records before it says it
is safe to `/clear`.

### Two landing strategies

*Parallel stacks* is removed, with its file-scope prediction, hotspot rule, and two-stack diagram.
The **serial stack** is the default: every bead in topological order, one branch atop the previous,
workers one at a time, each pull request linked into a GitHub stack as it opens. The **epic
branch** is the other: parallel waves off `epic/<id>-<slug>`, merged at wave boundaries, one
aggregate pull request. A later round's bead branches from the stack's one open top or from the
epic branch and is linked in the same way; nothing below it is touched by hand.

### Integration is GitHub's

When the frontier is empty, `implement` asks GitHub whether every open layer is mergeable and
points at the stack: the link to the top pull request — the most recent one, the one no other open
pull request bases on — and that merging it on GitHub lands the whole stack. Never a `gh` command,
and never a list of pull requests to merge in order from the bottom; the same link goes to every
persona, because the command adds nothing the link does not. `review` and `test` point at the stack
the same way when their run on an epic's work ends at the merge, and all three take the wording
from one section of `shared/stacks.md`, *Pointing at a stack*, rather than each carrying its own.
An epic branch's aggregate pull request, or a one-task run's single pull request, gets the same
sentence with its one link. A layer GitHub reports as conflicting or failing is fixed on the branch
that owns the change and cascaded with `gh stack rebase` and `gh stack push`. Nothing is rebased or
force-pushed by hand: the extension does the cascade, and GitHub does the rebase on merge.

## Consequences

- The epic and the spec's mirrored tracker issue stay open while any finding that is the epic's is
  open. A bug beside the epic does not hold the delivery, and the delivery stays the size of the
  feature.
- `bd children <epic>` answers whether a delivery is done, and the SessionStart prime already
  reports it.
- One count everywhere. The chart's done figure includes the landed bead and the amended records,
  so it reads a little lower than the tasks alone would, and it never disagrees with `bd`.
- The backlog reads as one list: `bd list -t bug -l area:<name>`, `--spec`, `--priority-max`,
  and `--metadata-field size=fix` each answer a question nobody could ask before. `fix` with no
  argument shows it and asks which one.
- Four verbs file bugs and none carries its own rule: the shared reference is the one place the
  classes, the scale, the area, and the fields are written, and a change there reaches every verb.
- The middle class is a judgment, stated as guidelines rather than a test, because a test strict
  enough to be mechanical punted bugs that blocked the epic. The person sees the call for each bug
  and changes it in the same answer. A run that shows the guidelines letting too much in or out
  changes them in the reference.
- A regression and a pre-existing bug are told apart in the graph, by `caused-by` against
  `discovered-from`, so what a delivery broke can be listed after the fact.
- `report` writes a bead now, so it needs Beads at step 10 and says the bead is pending when it is
  not; the report itself is still written. Its triage mode is the one path that changes a bead
  without a document, and it changes nothing unasked.
- A sweep gives the satisfaction of closing an epic to bug work, and `implement`, `review`, and
  `test` need no new mode for it: it is an epic whose children have no plan document, which
  tier-0 beads already are.
- Three verbs write to the epic: `implement` sets the round, and all three append to the notes.
  Notes are append-only by flag, so the three never collide.
- `plan`'s Revise mode compares only beads named `<prefix>-PLAN-NNN-Tn` against the table and
  lists the other children as the delivery's discovered work, never as dropped rows.
- `fix` refuses a bead whose epic still has open merge gates and names `implement`, because a fix
  lands on `main` and a delivery's work does not. With bugs beside the epic no longer parented to
  it, that refusal now meets only work that is the epic's.
- `delivery.sh` is built on `bd epic status --json` and does no counting of its own.
- The runs depend on the `gh-stack` extension for linking and cascading. A machine without it still
  gets the pull requests; the report says the stack was not linked and how to install it.
